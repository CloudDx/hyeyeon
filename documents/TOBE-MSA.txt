# Monolithic to Microservices Architecture (MSA) Refactoring Plan

## 1. 목표

기존의 Monolithic API에서 결제 관련 기능을 별도의 '결제 서비스' 마이크로서비스로 분리하고, RabbitMQ를 이용한 메시지 기반 통신으로 비동기 처리를 구현하여 시스템의 확장성과 유연성을 높입니다.

## 2. 신규 '결제 서비스' 정의

### 2.1. 책임
- 주문에 대한 결제 처리 및 상태 변경을 담당합니다.
- 기존 `app/main.py`의 `/pay/{order_id}` 엔드포인트 로직을 이관받습니다.

### 2.2. 구현 방안
- 새로운 Python FastAPI 애플리케이션으로 '결제 서비스'를 구성합니다.
- '결제 서비스'는 자체 데이터베이스를 가지거나, 기존 데이터베이스의 `orders`, `events` 테이블에 접근해야 합니다. MSA 원칙에 따라 자체 데이터베이스를 가지는 것을 권장하지만, 초기 단계에서는 기존 데이터베이스에 함께 접근하는 것으로 시작할 수 있습니다.

## 3. RabbitMQ 메시징 설계

### 3.1. 메시지 큐 정의
- `payment_request_queue`: 메인 앱에서 결제 서비스로 결제 요청을 보낼 때 사용합니다.
- `payment_result_queue`: 결제 서비스에서 처리 결과를 메인 앱으로 보낼 때 사용합니다.

### 3.2. 메시지 포맷
- **결제 요청 (메인 앱 -> 결제 서비스):**
  ```json
  {
    "order_id": "ord_...",
    "event_id": "evt_...",
    "qty": 1
  }
  ```
- **결제 결과 (결제 서비스 -> 메인 앱):**
  ```json
  {
    "order_id": "ord_...",
    "status": "PAID" | "FAILED",
    "event_id": "evt_...",
    "qty": 1
  }
  ```

## 4. 리팩터링 단계별 실행 계획

### 1단계: '결제 서비스' 프로젝트 생성
1.  `payment_service` 디렉터리를 새로 생성합니다.
2.  FastAPI 프로젝트를 기본 구조로 설정합니다. (`main.py`, `requirements.txt`, `Dockerfile` 등)
3.  `docker-compose.yaml`에 `payment_service`를 추가합니다.

### 2단계: '결제 서비스' 구현
1.  RabbitMQ `payment_request_queue`를 구독(consume)하는 로직을 구현합니다.
2.  메시지를 받으면, 기존 `app/main.py`의 `pay` 함수 로직을 수행하여 결제를 처리합니다.
    - 데이터베이스에서 주문 정보를 조회하고, 상태를 `PAID`로 변경합니다.
    - `events` 테이블의 `sold_qty`를 업데이트합니다.
    - `holds` 테이블에서 관련 데이터를 삭제합니다.
3.  처리 완료 후, `payment_result_queue`로 결과 메시지를 발행(publish)합니다.

### 3단계: 기존 '메인 앱' 리팩터링
1.  **`/pay/{order_id}` 엔드포인트 수정:**
    - 기존의 동기 처리 로직을 제거합니다.
    - 대신 `payment_request_queue`로 결제 요청 메시지를 보내는 로직을 추가합니다.
    - 사용자에게는 "결제 처리 중"이라는 상태를 즉시 반환합니다.
2.  **결과 처리 컨슈머 추가:**
    - `payment_result_queue`를 구독하는 RabbitMQ 컨슈머를 `app/consumer.py` 또는 별도 파일에 구현합니다.
    - 결제 결과 메시지를 받으면, 다음을 수행합니다.
        - WebSocket을 통해 클라이언트에게 `stock.update` 및 `order.update` 메시지를 브로드캐스트합니다.
        - 관련 로그를 기록합니다.

## 5. 데이터 일관성 유지 방안

- **Saga 패턴 (Choreography-based):** 각 서비스는 이벤트를 발행하고 다른 서비스는 해당 이벤트를 구독하여 자신의 작업을 수행합니다. 현재 설계는 이 패턴을 따릅니다.
  - 메인 앱: '결제 요청' 이벤트를 발행합니다.
  - 결제 서비스: '결제 요청'을 처리하고 '결제 완료' 이벤트를 발행합니다.
  - 메인 앱: '결제 완료' 이벤트를 구독하여 재고 및 주문 상태를 최종 업데이트합니다.
- **보상 트랜잭션:** 결제 실패 시, 결제 서비스는 '결제 실패' 이벤트를 발행하고, 메인 앱은 이를 받아 주문 상태를 'FAILED'로 변경하는 등의 보상 로직을 수행해야 합니다.

## 6. 향후 고려사항

- **API Gateway:** MSA가 더 복잡해지면, 클라이언트 요청을 단일 진입점에서 처리하고 각 마이크로서비스로 라우팅하는 API Gateway 도입을 고려할 수 있습니다.
- **분산 추적:** 서비스 간 호출을 추적하고 디버깅하기 위해 Jaeger, Zipkin 같은 분산 추적 시스템 도입을 검토합니다.

## 7. 적용 단계 (To-Do List)

이 섹션은 실제 코드 변경을 위한 구체적인 작업 목록입니다.

### **Phase 1: 결제 서비스 프로젝트 설정 [완료]**

1.  **디렉터리 생성:** 프로젝트 루트에 `payment_service` 디렉터리를 생성합니다.
2.  **기본 파일 생성:**
    - `payment_service/main.py`: 기본 FastAPI 앱 설정
    - `payment_service/database.py`: 데이터베이스 연결 로직
    - `payment_service/models.py`: `Order`, `Event`, `Hold` 모델 (기존 `app/models.py`에서 복사)
    - `payment_service/requirements.txt`: `fastapi`, `uvicorn`, `aio-pika`, `SQLAlchemy`, `psycopg2-binary` 등 필요 라이브러리 명시
    - `payment_service/Dockerfile`: 결제 서비스 컨테이너 빌드를 위한 Dockerfile 작성
3.  **`docker-compose.yaml` 수정:**
    - `services` 섹션에 `payment-service`를 새로 추가합니다.
    - `build`, `ports`, `environment` 등을 설정합니다.

### **Phase 2: 결제 서비스 로직 구현 (`payment_service/main.py`) [완료]**

1.  **RabbitMQ 연결:**
    - 기존 `app/main.py`의 `connect_rabbitmq` 함수를 참고하여 RabbitMQ 연결 및 채널 설정 로직을 구현합니다.
    - 애플리케이션 시작 시(`@app.on_event("startup")`) 실행되도록 설정합니다.
2.  **큐 선언:**
    - `payment_request_queue` (수신용)와 `payment_result_queue` (송신용)를 선언(`declare_queue`)하는 로직을 추가합니다.
3.  **결제 요청 컨슈머 구현:**
    - `payment_request_queue`를 구독하고 메시지를 비동기적으로 처리하는 `consume_payment_requests` 함수를 작성합니다.
    - 이 함수는 애플리케이션 시작 시 백그라운드 태스크로 실행되어야 합니다. (`asyncio.create_task`)
    - **메시지 처리 로직:**
        - 수신한 메시지(JSON)에서 `order_id`, `event_id`, `qty`를 파싱합니다.
        - 기존 `app/main.py`의 `pay` 함수에 있던 데이터베이스 트랜잭션 로직을 그대로 가져와 실행합니다.
            - `orders` 테이블의 상태를 `PAID`로 업데이트
            - `events` 테이블의 `sold_qty` 증가
            - `holds` 테이블의 관련 항목 삭제
4.  **결제 결과 발행:**
    - 결제 처리가 성공하면, `payment_result_queue`로 결과 메시지를 발행(`publish`)합니다.
    - 메시지 내용: `{ "order_id": "...", "status": "PAID", "event_id": "...", "qty": ... }`

### **Phase 3: 메인 앱 리팩터링 (`app/` 디렉터리) [완료]**

1.  **`/pay/{order_id}` 엔드포인트 수정 (`app/main.py`):**
    - 기존의 데이터베이스 처리 로직을 **모두 제거**합니다.
    - `order_id`로 `orders` 테이블을 간단히 조회하여 `event_id`와 `qty`를 가져옵니다.
    - **결제 요청 메시지 발행:**
        - `aio_pika.Message`를 생성합니다. Body에는 `order_id`, `event_id`, `qty`가 포함된 JSON 문자열을 담습니다.
        - `rabbitmq_channel.default_exchange.publish`를 호출하여 `payment_request_queue` 라우팅 키로 메시지를 보냅니다.
    - 클라이언트에게는 `{"ok": True, "status": "PAYMENT_PROCESSING"}` 과 같은 즉각적인 응답을 반환합니다.
2.  **결제 결과 컨슈머 구현 (`app/consumer.py` 신규 생성 또는 `app/main.py`에 추가):**
    - `payment_result_queue`를 구독하는 컨슈머를 작성합니다.
    - 이 컨슈머는 메인 앱 시작 시 백그라운드 태스크로 실행되어야 합니다.
    - **메시지 처리 로직:**
        - 수신한 메시지에서 `order_id`, `status`, `event_id` 등을 파싱합니다.
        - `status`가 `PAID`이면, 기존 `pay` 함수의 후반부에 있던 **브로드캐스트 로직**을 실행합니다.
            - `current_remaining` 함수로 최신 재고 정보를 가져옵니다.
            - `manager.broadcast`를 사용하여 `stock.update`와 `order.update` WebSocket 메시지를 모든 클라이언트에게 전송합니다.
        - 관련 성공/실패 로그를 기록합니다.
3.  **RabbitMQ 큐 선언 수정 (`app/main.py`):**
    - 기존 `hello` 큐 외에, `payment_request_queue`와 `payment_result_queue`도 선언하도록 `connect_rabbitmq` 함수를 수정합니다.

### **Phase 4: 전체 시스템 테스트**

1.  **빌드 및 실행:** `docker-compose up --build` 명령으로 모든 서비스(메인 앱, 결제 서비스, RabbitMQ, DB)를 실행합니다.
2.  **E2E 테스트:**
    - `/purchase` API를 호출하여 주문 및 좌석 홀드를 생성합니다.
    - 수정된 `/pay/{order_id}` API를 호출합니다.
    - **검증:**
        - `/pay` API가 즉시 응답을 반환하는지 확인합니다.
        - 잠시 후, WebSocket 클라이언트가 `stock.update` 및 `order.update` (상태: PAID) 메시지를 수신하는지 확인합니다.
        - 데이터베이스에서 `orders` 테이블의 상태, `events`의 `sold_qty`, `holds` 테이블의 데이터 삭제 여부를 직접 확인하여 데이터 일관성을 검증합니다.
